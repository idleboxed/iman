# Конфигурация iman

Менеджер читает два независимых JSON-файла из `system/iman/`:

- `iman.json` — окружение сеанса и запуск IGUI;
- `emulation.json` — RetroArch, ядра и настройки игр.

Поля версии схемы нет. Неизвестные поля игнорируются; обязательные поля,
типы и значения перечислений проверяются. Каждый файл ограничен 64 КиБ.
Изменение JSON не добавляет поддержку полей в старый бинарник.

## Профиль сеанса

Пример `iman.json` для DRM:

```json
{
  "runtime_dir": "/tmp",
  "gui": {
    "display": {
      "backend": "drm",
      "device": "/dev/dri/card0",
      "allow_vendor_einval": false
    }
  }
}
```

Это выбор окружения, не настройка или проверка конкретной платы.
Используйте существующий tmpfs; профиль с `/tmp` недопустим, если этот каталог
находится на дисковой ФС. Менеджер может создать только отсутствующий последний
компонент под проверенным tmpfs, но не дерево родительских каталогов.

| Поле | Значение и ограничения |
|---|---|
| `runtime_dir` | Абсолютный путь; по умолчанию `/dev/shm`. tmpfs проверяется при запуске. |
| `gui.display.backend` | `desktop` по умолчанию, `headless` или `drm`. |
| `gui.display.device` | Для DRM: абсолютный путь, по умолчанию `/dev/dri/card0`. |
| `gui.display.connector` | Для DRM: необязательный положительный ID коннектора. |
| `gui.display.allow_vendor_einval` | Для DRM: явное разрешение совместимости с драйвером производителя, по умолчанию `false`. |
| `gui.frames` | Необязательное положительное ограничение кадров IGUI. |
| `gui.hid_profile`, `gui.evdev_profile` | Необязательные непустые пути к профилям ввода IGUI. |

Относительные пути профилей ввода считаются от каталога `iman.json`,
не от текущего рабочего каталога. Их формат и проверка принадлежат IGUI.
`headless` не допускает `frames` и профилей ввода. `desktop` создаёт окно
самого менеджера только при feature `pc`; без неё вывод остаётся за дочерним процессом.
`drm` требует feature `drm`, рабочего устройства и согласованных настроек RetroArch.

Автозагрузка, явный `--config` и аргументы, передаваемые IGUI напрямую, описаны в
[контракте запуска](runtime.md#запуск-в-linux).
Реализация профиля — [`profile.rs`](../src/profile.rs).

## Манифест эмуляции

Пример структуры `emulation.json` для Linux x86_64:

```json
{
  "architecture": "x86_64",
  "retroarch": {"path": "retroarch/retroarch"},
  "cores": {
    "NES": {"path": "retroarch/cores/nestopia_libretro.so"}
  },
  "settings": {
    "video_driver": "gl",
    "video_context_driver": "x",
    "input_driver": "udev",
    "input_joypad_driver": "udev",
    "audio_driver": "alsa",
    "autosave_interval": 60
  }
}
```

Пример не заменяет подготовку бинарников, каталога игр и драйверов хоста.
`architecture` должна совпадать с архитектурой iman (`arm` для ARMv7,
`x86_64` для соответствующей ПК-сборки). ABI и совместимость ядра/эмулятора
не определяются одной строкой JSON.

Пути компонентов и шейдеров относительны `system/`, не каталогу JSON.
Платформа из запроса IGUI выбирает запись `cores.<PLATFORM>`; менеджер
не определяет её по расширению ROM и не содержит реестра поддерживаемых ядер.
Полный манифест нужен для игр, но не обязателен для сеанса только с GUI.
Повреждённый существующий манифест не игнорируется.

### Настройки RetroArch

`settings` — объект уникальных имён со скалярными значениями:
строками, логическими и JSON-числами. Вложенные объекты, массивы и `null`
не допускаются. Имя — до 128 байт из ASCII-букв, цифр и `_`.
Строка — до 16 КиБ, без управляющих символов, кавычек и обратной косой черты.

Менеджер исключает пользовательские значения своих ключей и добавляет
[политику хранения](../src/emulation/retroarch-policy.cfg) и вычисленные пути.
Настройки не могут включить неявное сохранение конфигурации/истории или
перенаправить управляемые временные файлы на SD. `autosave_interval`
не перекрывается менеджером: значение 60 задаёт профиль комплекта.

Для передачи DRM между меню и игрой требуется `video_context_driver: "kms"`.
Остальные драйверы выбираются для хоста, а не угадываются по названию платы.
Разбор и сериализация — [`emulation`](../src/emulation/mod.rs),
выбор компонентов — [`launcher`](../src/emulation/launcher.rs).

## Шейдеры по платформам

Необязательное `cores.<PLATFORM>.shader_preset` выбирает `.glslp`
относительно `system/`:

```json
{
  "cores": {
    "NES": {
      "path": "retroarch/cores/nestopia_libretro.so",
      "shader_preset": "retroarch/shaders/presets/NES.glslp"
    }
  }
}
```

Это фрагмент манифеста. Выбор зависит от платформы запроса: две платформы
могут использовать одно ядро с разными пресетами.
Отсутствующее поле или `null` отключает шейдеры. Менеджер задаёт
`video_shader_enable` и отдельный аргумент RetroArch `--set-shader`;
пользовательское значение этого переключателя не создаёт повторного ключа.
`auto_shaders_enable` остаётся выключенным.

Главный файл пресета проверяется до запуска: относительный путь `.glslp`,
обычный файл с одной жёсткой ссылкой, отсутствие симлинков в пути, та же ФС, размер до 1 МиБ.
Ошибка явно выбранного файла останавливает подготовку игры.
RetroArch сам читает вложенные `#reference`, текстуры и проходы из исходного
расположения, без копии в RAM и собственного парсера iman.
Проверка главного файла не изолирует всю цепочку файлов и не гарантирует GLSL/FPS.

## Переназначение управления

Для платформы можно задать `library_name` и `remap`:

```json
{
  "cores": {
    "FDS": {
      "path": "retroarch/cores/nestopia_libretro.so",
      "library_name": "Nestopia",
      "remap": {
        "input_player1_btn_x": 10,
        "input_player1_btn_y": 11
      }
    }
  }
}
```

Здесь X/Y первого RetroPad становятся L/R (10/11), не физическими кнопками USB.
Значение действий определяет ядро. Это пример механизма, не особое правило FDS
в коде iman и не полный профиль контроллера.

`remap` использует скалярные параметры RetroArch с ограничениями `settings`;
имя дополнительно допускает один завершающий `+` или `-` для оси.
Отсутствующее поле или `{}` не создаёт профиль; `null`, повторные ключи,
вложенные значения и опасные строки отклоняются.

Для непустого `remap` обязательно точное имя из `retro_get_system_info`,
с учётом регистра, а не имя `.so`. `library_name` — до 128 байт, непустое,
без внешних пробелов, разделителей пути, кавычек и управляющих символов;
`.` и `..` запрещены. Менеджер не загружает ядро ради определения имени.
Неверное имя может привести к тому, что RetroArch не найдёт профиль.

Файл `remaps/<library_name>/<library_name>.rmp` создаётся только в приватном
tmpfs запуска, без перезаписи существующих путей или следования симлинкам.
Менеджер включает `auto_remaps_enable` и `input_remap_binds_enable`,
отключает сортировку по имени контроллера и сохраняет `remap_save_on_exit=false`.
Пользовательские `settings` не могут отменить выбранный профиль или RAM-пути.
Изменения в меню RetroArch не заменяют постоянный источник `emulation.json`;
временный каталог удаляется после игры. Реализация — [`remap`](../src/emulation/remap.rs).

## Параметры ядра и системный каталог

Поля `system_directory` и `core_options` принадлежат записи платформы:

```json
{
  "cores": {
    "N64": {
      "path": "retroarch/cores/mupen64plus_next_libretro.so",
      "system_directory": "ram",
      "core_options": {
        "mupen64plus-43screensize": "320x240",
        "mupen64plus-EnableTextureCache": "False"
      }
    }
  }
}
```

`system_directory` принимает `"bios"` (по умолчанию) или `"ram"`.
`"ram"` всегда выбирает пустой системный каталог в RAM, не открывая
`system/bios/<PLATFORM>`. Этот вариант подходит ядрам, создающим INI-файлы или кэш
в системном каталоге; обратная сторона — отсутствие BIOS оттуда.

`core_options` по умолчанию пуст. Допускается до 128 уникальных ключей
со строковыми значениями, до 32 КиБ итогового CFG.
Имя — до 128 байт, начинается с ASCII-буквы/цифры и содержит только
буквы, цифры, `_` и `-`. Значения — до 16 КиБ с ограничениями строк `settings`.
Регистр сохраняется: `"False"` не заменяется JSON `false`.

`core-options.cfg` создаётся эксклюзивно через удерживаемый FD проверенного
tmpfs. `settings` не могут заменить `core_options_path`, `global_core_options`
или управляемые пути. Политика SRAM и постоянных сохранений не меняется.
Реализация — [`core_options`](../src/emulation/core_options.rs).
Конкретные назначения и обновление готовых профилей принадлежат сборщику комплекта.

## BIOS

Политика `"bios"` передаёт существующий `system/bios/<PLATFORM>/` напрямую
ядру, без копирования в RAM, списков обязательных файлов и правил точных размеров.
Какие BIOS нужны, определяет ядро; добавление файла для поддержанной платформы
не требует пересборки iman.

Компоненты пути проверяются через `O_DIRECTORY` и `O_NOFOLLOW`; они должны находиться на одной ФС.
Содержимое дерева не обходится. При отсутствии каталога используется пустой
RAM-каталог `bios/`, без создания файлов на SD и резервного перехода на каталог ROM.
**Прямой путь не запрещает ядру писать в системный каталог, пока носитель RW.**
Для ядра с такими записями выбирайте `"ram"`, учитывая его требования к BIOS.
Реализация — [`bios`](../src/emulation/bios.rs).

О сообщениях отказа и постоянных данных — в
[контракте сеанса](runtime.md#ошибки-запуска).
